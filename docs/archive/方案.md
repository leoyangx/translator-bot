## 1. 产品形态：一个"翻译工作台"

不是"发一句翻一句"的玩具，而是覆盖你真实动作的五个入口：

| 入口 | 你的动作 | 机器人的反应 |
|---|---|---|
| **转发** | 把任意韩语消息转发给它 | 引用原文 + 中文译文（双语对照） |
| **粘贴** | 从 WhatsApp 等处复制文字发过来 | 自动识别方向，直接译 |
| **回复** | 在群里回复某条韩语消息并 @ 它 | 只翻那一条，不刷屏 |
| **语音** | 转发韩语语音 | 转写原文 + 中文译文 |
| **截图** | 发一张韩语截图 | 直接出中文（视觉模型一步到位，不做 OCR 拼装） |

每条译文下面带一排按钮：`换个说法` `更正式` `更口语` `解释一下` `原文`。
——这是"翻得不准时"的兜底，比重新组织一句话再发一遍快得多。

**双向**：你说中文，它译成韩语，默认敬语体（존댓말），可直接复制回 WhatsApp 发给对方。聊天场景里，"能回话"往往比"能看懂"更刚需。

## 2. 技术栈

| 层 | 选型 | 为什么 |
|---|---|---|
| 语言 | Python 3.12 | Telegram / 语音 / 图片生态最全，出问题最好查 |
| Bot 框架 | aiogram 3 | 异步、长轮询稳定、社区活跃；比自写 HTTP 轮询可靠得多 |
| 模型接入 | `openai` 官方 SDK + `base_url` | 一套代码通吃 DeepSeek / 通义 / 智谱 / OpenRouter / Ollama |
| 存储 | SQLite（单文件） | 零运维，缓存 + 术语表 + 设置 + 用量都在里面 |
| 语音 | faster-whisper（本地，跑显卡） | 不花钱、不联网、不上传；1060 跑 small/medium 足够 |
| 图片 | 视觉模型（Qwen-VL / GLM-4V，走兼容接口） | 比"OCR + 翻译"两步少一半故障点，韩文竖排/艺术字也认得 |
| 常驻 | Windows 服务（NSSM） | 开机自启、崩溃自动拉起、不需要登录桌面 |
| 配置 | `config.yaml`（3 个必填项） | 你只改 token / key / 代理，其余在机器人里点按钮改 |

**不引入**：Docker、数据库服务、消息队列、Web 后台。个人工具，每多一层就多一个半夜挂掉的理由。

## 3. 翻译引擎策略

### 3.1 主引擎：DeepSeek（OpenAI 兼容）

```
base_url: https://api.deepseek.com
model:    deepseek-chat
```

- 韩→中质量在"日常聊天 / 新闻 / 商品 / 客服"这些场景里属于第一梯队，敬语、缩略语、语序都能处理；
- 大陆、香港都能直连，不需要代理（这点很关键，Telegram 已经要代理了，模型别再要一个）；
- 便宜到可以忽略，个人重度使用每月也就几块钱；
- 换成通义、智谱、硅基流动、OpenRouter、本地 Ollama，只改 `config.yaml` 三行。

### 3.2 多供应商 + 故障转移

配置里写一组 `providers`，按顺序尝试，超时/429/5xx 自动切下一个。避免"某家抽风，机器人就哑了"。

### 3.3 1060 的真实定位（不吹）

| 用途 | 可行性 | 说明 |
|---|---|---|
| 本地语音识别 | ✅ 推荐 | faster-whisper small/medium，短语音 1～3 秒出结果 |
| 本地大模型翻译 | ⚠️ 兜底 | 7B Q4 勉强塞进 6GB，速度 10～15 字/秒，韩中质量明显低于 DeepSeek，**不建议做主引擎** |
| 本地 OCR | ✅ 可行 | 但已被"视觉模型直接翻"取代，不做 |

结论写在配置里：`engine: deepseek`，另留 `local` 作为断网/欠费时的备胎。

## 4. 质量从哪里来（比换模型更重要）

| 手段 | 做法 | 效果 |
|---|---|---|
| 固定输出规范 | system prompt 锁死"只输出译文"，保留换行/emoji/数字/单位/人名 | 不会被模型的自言自语污染 |
| 术语表 | `/addterm 김치 = 泡菜`，翻译时强制注入 | 人名、公司名、游戏术语前后一致，这是机器翻译最烦人的地方 |
| 上下文 | 同一会话带最近 3～5 条原文 | 韩语大量省略主语，这一项提升最明显 |
| 语气档位 | 直译 / 自然 / 商务 / 字幕 | 聊天、看新闻、发邮件不是一个腔调 |
| 缓存 | 文本哈希去重 | 同一句转发两次不重复花钱，也更快 |
| 长文分块 | 按段落切，保留 4096 字符限制 | 长文章不会截断或报错 |
| 失败留样 | 你点"翻得不对"，把样本存下来 | 之后调 prompt / 补术语表有依据 |

## 5. 部署与运维（面向"不会写代码"）

### 5.1 目录

```
翻译机器人/
├─ app/              源码（你不用碰）
├─ config.yaml       唯一需要你填的文件：Token、API Key、代理
├─ 安装.bat          双击一次：装 Python 依赖 + 注册开机自启
├─ 启动.bat / 停止.bat
├─ 更新.bat
├─ logs/             中文日志，出问题直接发我
├─ data/bot.db       缓存、术语表、用量
└─ 使用说明.md / 故障排查.md
```

### 5.2 网络（唯一真正的门槛）

- **大陆**：`api.telegram.org` 不通，必须给机器人单独配代理。配置里写：
  ```yaml
  proxy: socks5://127.0.0.1:7890   # 换成你自己客户端的本地端口
  ```
  ⚠️ **Windows 系统代理对 Python 无效**，必须写进配置，这是最常见的"装了但没反应"。
- **香港**：一般直连可用，`proxy:` 留空即可，启动自检会自动判断。

### 5.3 常驻

- NSSM 注册成服务：开机自启、崩溃 5 秒后自动重启、不弹黑框；
- 电源计划设"从不睡眠"（或接受电脑关机时机器人离线）；
- Telegram 会给离线机器人保留约 24 小时消息，重启后必须**跳过超过 10 分钟的旧消息**，否则一开机炸出一屏过期翻译。

### 5.4 自检与排障

`/doctor` 一次性检查并给出中文结论：网络能否到 Telegram、代理是否生效、API Key 是否有效、模型是否可调、磁盘与日志、当前引擎与今日花费。
你只需要把这个输出发给我，我就能定位问题——这是"不会写代码"能被支持的前提。

## 7. 分期计划与验收

每一期都能独立使用，任何一期不通就停下，不继续投入。

### 阶段 0 · 连通性验证（30～60 分钟）★ 决定项目成败
- 装 Python、建虚拟环境、拉依赖（走国内镜像）
- BotFather 建 Bot 拿 Token；DeepSeek 开 Key 充 10 元
- 跑一个最小回显 + 一次真实翻译
- **验收**：在 Telegram 里发"안녕하세요"，3 秒内收到"您好"

> 这一步专门用来回答你那个问题——"你是不是百分之百有把握"。网络这一关过了，后面都是确定性的活。

### 阶段 1 · 文本 MVP（约 1 天）
转发 / 粘贴 / 回复三种触发；双向翻译；双语对照；白名单；开机自启。
**验收**：连续转发 20 条真实韩语，全部可用，顺序不乱。

### 阶段 2 · 好用（1～2 天）
术语表、语气按钮、上下文、缓存、`/doctor`、`/stats`、长文分块。
**验收**：固定人名/术语 10 条全部译法一致；断网 30 秒后自动恢复。

### 阶段 3 · 语音与图片（1～2 天，依赖实测）
本地 Whisper 跑 1060；截图走视觉模型。
**验收**：1 分钟韩语语音，转写 + 译文可读；韩语截图能整段译出。

### 阶段 4 · 交付打磨（0.5～1 天）
一键安装脚本、中文说明书、故障排查手册、日志清理、数据库备份。

## 10. 置信度说明（就你问的"百分之百"）

**高把握（约等于确定）**：文本双向翻译、术语表、语气切换、上下文、缓存、服务化自启、日志、自检、一键脚本。这些都是成熟组件的组合，没有研究性风险。

**需实测（有把握但不敢说死）**：1060 上本地语音的速度与准确度（与 CUDA 环境有关，装不上就退回 CPU，慢一点但能用）；视觉模型对韩语截图的识别率（竖排、艺术字可能失手，可用"发文字"兜底）。

**不可控（不在我能力范围内）**：你的代理是否稳定、电脑是否长期开机、第三方 API 是否改价改接口、Windows 是否会拦服务。

**应对方式**：阶段 0 先验证网络与密钥；引擎可切换 + 故障转移；所有失败都有中文提示和日志；代码在这个工作区，坏了随时修。

所以我不说"百分之百"，我说的是：**每一段都可验证，任何一段不通就停在那里，不会让你白花钱。**

## 附：MuseBot 评估（2026-10-31）

仓库：https://github.com/yincongcyincong/MuseBot （Go，MIT，Telegram/Discord/Slack/飞书/钉钉/企微/QQ/微信，DeepSeek/OpenAI/Gemini/Qwen/Doubao/Ollama）

**定位**：通用 AI 聊天机器人，不是翻译机器人。可读的代码里没有任何翻译专有功能（术语表、双语、语种方向、缓存）。

| 需求 | 支持度 | 说明 |
|---|:---:|---|
| Telegram + DeepSeek + OpenAI 兼容 | ✅ | `TYPE=deepseek`，`CUSTOM_URL` 可换任意兼容服务 |
| 大陆代理 | ✅ | `ROBOT_PROXY` / `LLM_PROXY` 分开配 |
| 白名单 | ✅ | `ALLOWED_USER_IDS` |
| 中文界面 / 用量统计 | ✅ | `LANG=zh`、`/state` |
| 转发即翻、双语对照 | ❌ | 没有"翻译卡片"这层结构 |
| 术语表、语气档位、缓存 | ❌ | 需改代码 |
| 双向自动识别 | ❌ | 只能靠 `CHARACTER` 提示词约束 |
| 语音 | ⚠️ | 需音频模型（Qwen/Gemini），DeepSeek 不支持 |
| 截图翻译 | ⚠️ | 需视觉模型，且走 `/task` 流程 |
| Windows 一键部署 | ⚠️ | Go 构建或 Docker，无现成 exe |

**结论**：可以作为"通用助手"用，不适合当翻译底座。原因：`SMART_MODE` 会把长文本判成复杂任务交给 `/task` 多智能体；对话记忆（`MAX_QA_PAIR=100`）会让前后译文互串；语音/图片在 DeepSeek 下不可用，要再引入一套模型配置。二次开发要在 Go 大项目里写插件，维护成本高于自建 400 行小服务。

**可借鉴**：代理配置拆成 bot/LLM 两条、模型故障转移、`/state` 用量统计——这三点吸收进本方案。
